QUESTION 151Insurance code & design analysis#

151. Why store insurance claims in relational tables instead of only vector documents?

Read / reveal answer

Claims have exact ownership, monetary amounts, lifecycle states, references, and transaction boundaries. A vector index optimizes similarity retrieval and does not replace those relational invariants. The same claim can have an authoritative row and a derived search representation.

Mechanism & reason

Claim maps UUID identity, a unique human-readable claim_id, owner_id, Numeric amount, timestamps, and search columns. Submission and lifecycle routes update business state, while embedding jobs maintain retrieval data.

Risk & safeguards

Treating the vector record as the sole source of truth makes exact authorization, status transitions, and recovery dependent on a derived index. Search ranking cannot decide whether a claim exists or who owns it.

Choice & trade-offs

Relational plus search modeling creates projection maintenance work but supports exact operations and flexible discovery. A text-only prototype is smaller and insufficient for authoritative workflows.

152. Why have both a UUID primary key and a human-readable claim ID?

Read / reveal answer

A UUID provides an internal identifier suitable for references; a separate claim ID provides a support-friendly external label. They have different display and collision properties. Neither identifier should be treated as an authorization secret.

Mechanism & reason

The model uses a UUID primary key and a unique claim_id. Submission generates the external identifier from a shortened UUID fragment, so uniqueness is ultimately enforced by the database constraint rather than guaranteed by formatting.

Risk & safeguards

Shortened random identifiers can collide. A production collision-handling path should distinguish a retryable uniqueness conflict from unrelated database errors, and users must still be scoped even when an ID is known.

Choice & trade-offs

Friendly IDs improve support and communication while adding an extra index and identity mapping. Full opaque IDs are simpler but awkward to read aloud.

QUESTION 153Insurance code & design analysis#

153. Why use Numeric and Decimal for claim amounts?

Read / reveal answer

Decimal arithmetic and a fixed-scale Numeric column represent monetary values more predictably than binary floating point. Currency precision, rounding, allowed scale, and upper bounds are part of the domain contract rather than formatting details.

Mechanism & reason

Claim.amount uses Numeric(12,2), and preparation serializes the validated Decimal as a string in JSONB. The confirmation route converts that string to float before calling the internal function, which is an observed precision boundary worth revisiting.

Risk & safeguards

A Decimal column cannot retroactively undo precision lost earlier in JSON parsing, float conversion, or arithmetic. Validation and serialization must preserve the intended amount end to end.

Choice & trade-offs

Decimal values need explicit JSON handling and careful provider-tool schemas. Float is convenient for generic numeric tools but weakens exact-money guarantees.

QUESTION 154Insurance code & design analysis#

154. How do foreign keys, unique constraints, and check constraints complement application validation?

Read / reveal answer

Application validation gives useful error messages; database constraints protect against every writer sharing the database. Foreign keys preserve references, unique constraints enforce identity rules, and check constraints reject invalid row-level values even when a route is bypassed.

Mechanism & reason

Claim.owner_id references users and claim_id is unique. The embedding outbox explicitly documents that claim_uuid has no foreign key, making transactional enqueue discipline important. Not every Python enum is automatically a database-level constraint.

Risk & safeguards

Assuming all invariants are enforced because ORM types exist leaves gaps for scripts, workers, and future routes. Constraints also need deliberate delete and migration behavior.

Choice & trade-offs

Strong constraints simplify consistency reasoning but can complicate staged migrations and bulk imports. Relaxing them requires another proven enforcement mechanism.

QUESTION 155Insurance code & design analysis#

155. What belongs in normalized columns versus JSONB?

Read / reveal answer

Put fields used for relationships, strict constraints, frequent filtering, and stable reporting in typed columns. JSONB is useful for variable event payloads or a prepared-form snapshot. Its flexibility does not remove the need for schema versions, validation, or selective indexing.

Mechanism & reason

Claims use explicit business columns, while pending submissions and agent events store JSON structures. This lets preparation retain a reviewed request without immediately creating the final claim, and lets the runtime serialize framework events.

Risk & safeguards

Unversioned JSON can become unreadable after schema changes. Copying an entire stale state blob can also overwrite concurrent updates, while arbitrary JSON may retain more private data than needed.

Choice & trade-offs

JSONB speeds evolving payloads and weakens some relational guarantees. Normalize stable, high-value fields instead of treating the database as a dictionary with no contracts.

QUESTION 156Insurance code & design analysis#

156. Why does the owner-and-created-at composite index matter?

Read / reveal answer

The claim list filters by owner and orders by creation time. An index beginning with owner_id and then created_at can support that access pattern more directly than two unrelated indexes. Index design should follow real predicates, ordering, and pagination.

Mechanism & reason

Claim declares ix_claims_owner_id_created_at with both columns, alongside a GIN index for tsvector. These indexes serve different query families: exact scoped listings and lexical search.

Risk & safeguards

An index declaration does not prove an efficient plan at production data sizes. Additional sort keys, selective predicates, and row estimates can change the plan; unused indexes still cost writes and storage.

Choice & trade-offs

More indexes accelerate selected reads while slowing mutation and increasing maintenance. Validate with representative EXPLAIN plans rather than indexing every column reflexively.

QUESTION 157Insurance code & design analysis#

157. How do policy versions differ from current policy chunks?

Read / reveal answer

A policy version records the source and indexing configuration over time. Policy chunks are searchable material for a version. Keeping version records does not necessarily mean every historical chunk remains retained or that a query selects the contract applicable to an incident.

Mechanism & reason

PolicyVersion records effective dates, source_hash, embedding information, and chunking settings. The host policy retrieval spec exposes section and source metadata but not a complete incident-date and policy-entitlement selection contract.

Risk & safeguards

Current-source retrieval can answer the wrong historical question even when its text is accurately quoted. Historical evidence needs both retention and an explicit applicable-version filter.

Choice & trade-offs

Retaining every version supports audits and costs storage and selection logic. Current-only indexing is simpler and must state its scope honestly.

QUESTION 158Insurance code & design analysis#

158. Why use Alembic migrations instead of create_all for production evolution?

Read / reveal answer

create_all creates missing schema objects represented in current metadata; it is not a reviewed sequence for changing existing columns, backfilling data, or coordinating old and new application versions. Migrations record explicit upgrade steps and dependencies.

Mechanism & reason

The backend has Alembic revisions for claim dates, policy versions, audit records, jobs, and evaluation runs. database.py labels create_all_tables for development and CI. Agent session tables are a separate runtime-owned create_all exception.

Risk & safeguards

Treating all schema as migration-owned overlooks that exception. Concurrent startup and runtime DDL require operational planning, and a failed migration must not leave an apparently healthy service using an incompatible schema.

Choice & trade-offs

Migrations add review and deployment sequencing but make history inspectable. Runtime creation is convenient for framework state and harder to govern consistently.

QUESTION 159Insurance code & design analysis#

159. What is an expand-and-contract migration?

Read / reveal answer

Add a compatible schema surface first, deploy code that can read old and new forms, backfill safely, switch writers, then remove the old form in a later release. The sequence allows rolling deployment and rollback without requiring every process to switch simultaneously.

Mechanism & reason

This is a proposed deployment method for evolving the insurance schemas, not proof that every existing migration follows it. New incident-date or money-handling fields are concrete opportunities to reason about old rows and older workers.

Risk & safeguards

A backfill can hold locks or overload the database; a destructive cleanup can make application rollback impossible. Background jobs may also contain payloads written by an older schema version.

Choice & trade-offs

Compatibility periods increase temporary complexity and reduce deployment coupling. A single destructive migration is shorter and can require a maintenance window.

QUESTION 160Insurance code & design analysis#

160. How should you model authoritative events versus derived projections?

Read / reveal answer

ClaimEvent records lifecycle history; Claim.status is a current-state projection. Embedding records and notifications are downstream projections. Agent session events describe runtime execution, while audit events describe selected high-value actions. These logs are related but not interchangeable event-sourcing systems.

Mechanism & reason

The backend persists claim transitions and outbox work within business transactions. It separately records observability and audit information, each with different failure policy and consumers.

Risk & safeguards

Calling any append-only table event sourcing overstates replayability. A complete event-sourced design needs sufficient immutable events, deterministic projection rebuilding, versioning, and a declared source of truth.

Choice & trade-offs

Current rows plus a transition trail provide useful history with lower complexity. Full event sourcing improves replay options and adds substantial schema and operational obligations.
