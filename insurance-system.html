QUESTION 141Insurance code & design analysis#

141. What does the insurance backend add beyond the Ragnor subsystem?

Read / reveal answer

OmniCare supplies FastAPI routes, authenticated users, claims and policies, an ADK agent, confirmation workflows, persistent conversation history, background jobs, evaluation bindings, and observability. Ragnor remains a dependency providing retrieval infrastructure. A library capability and an application using that capability are separate implementation claims.

Mechanism & reason

pyproject.toml declares ragnor[pgvector], google-adk, LiteLLM, LangSmith, SQLAlchemy, and FastAPI. Agent construction uses LlmAgent and a tool registry; domain adapters bind generic retrieval to concrete tables. This is the real host that the first fourteen chapters discussed abstractly.

Risk & safeguards

Do not infer that every newer Ragnor feature is integrated. The policy tool concatenates retrieved context directly; it does not automatically use the library's full EvidenceAssembler and revision-lookup contract.

Choice & trade-offs

A narrow host binding is easier to ship, while richer evidence contracts add explicit statuses and provenance. Adoption requires wiring and migration rather than only upgrading a dependency.

QUESTION 142Insurance code & design analysis#

142. Which framework actually controls the agent loop?

Read / reveal answer

Google ADK controls the current agent loop through LlmAgent and Runner. LiteLLM adapts model access. Ragnor retrieves evidence. LangSmith observes execution. These packages occupy different layers; LangSmith's presence does not mean LangChain controls orchestration.

Mechanism & reason

create_agent passes a LiteLlm model, reviewed instructions, registered handlers, and a before-model history callback to LlmAgent. No LangGraph graph or A2A server is constructed by this path.

Risk & safeguards

Framework confusion leads to examples that cannot run against the project's dependencies. The later LangChain, LangGraph, and A2A chapters explicitly describe alternatives or additions rather than pretending those frameworks are already installed.

Choice & trade-offs

Staying with one orchestrator reduces state-model overlap. Adding another can solve a measured workflow need but introduces serialization, tracing, error, and deployment boundaries.

QUESTION 143Insurance code & design analysis#

143. How does a coverage question differ from a claim-status question?

Read / reveal answer

Coverage requires retrieving policy language and applying a reviewed procedure to the user's facts. Claim status is a lookup of structured application state under the authenticated owner's scope. An answer about a policy is evidence-based interpretation; an answer about an existing claim must reflect the actual recorded claim.

Mechanism & reason

The registry exposes query_policy, get_procedure, get_claim_status, and search_claims as distinct tools. Known claim IDs route to exact lookup; vague references route to owner-scoped semantic search.

Risk & safeguards

Semantic similarity cannot establish that an arbitrary claim ID belongs to the user or that a policy provision applies to their contract. Tool-side identity checks remain necessary even when prompting selects the right tool.

Choice & trade-offs

Separate tools make intent and authority clearer but require route-selection evaluation. One universal search tool is simpler and can blur exact facts with approximate matches.

QUESTION 144Insurance code & design analysis#

144. What is the difference between an agent session and a conversation record?

Read / reveal answer

Agent sessions hold runtime state and events used by ADK. Conversation records hold application-visible messages, ownership, archival state, and IDs used by feedback and history APIs. They overlap in content but serve different contracts and lifecycle requirements.

Mechanism & reason

agent.py defines session storage and replay, while conversation_store.py persists chat turns. The before-model callback can rehydrate recent history from conversation messages. Persistent chat history therefore does not by itself prove persistent runtime state.

Risk & safeguards

Divergence can replay a turn twice, omit tool results, or show UI messages that the agent cannot recall. Switching storage modes also needs a deliberate migration and restart story.

Choice & trade-offs

Separate stores decouple product history from runtime implementation but require clear reconciliation and retention ownership. A single store reduces duplication and can bind the product tightly to one framework.

QUESTION 145Insurance code & design analysis#

145. What is the real prepare-and-confirm boundary for claim creation?

Read / reveal answer

Preparation validates fields and stores a pending submission with a confirmation token and expiry. Confirmation is an authenticated API operation that locks the pending submission, creates the claim and associated records, marks completion, and commits. Agent prose does not itself complete the financial workflow.

Mechanism & reason

The model-facing registry includes prepare_claim_submission, while submit_claim_internal is reached through the confirmation route. This preserves a server-side boundary between collecting intent and applying an authoritative write.

Risk & safeguards

The prompt's phrase that a tool call is the confirmation action can be misunderstood. The actual database submission still requires the separate route. A textual yes from the model is not proof that the API operation succeeded.

Choice & trade-offs

Two steps add user interaction and pending-state management while reducing accidental writes. A one-step workflow is faster but gives less opportunity to review material fields.

QUESTION 146Insurance code & design analysis#

146. Why separate policy procedures from policy facts?

Read / reveal answer

A procedure describes how to investigate a question or route an unclear request. A policy source supplies actual limits, deductibles, exclusions, and conditions. The procedure should not become an alternative authority for contractual facts merely because it is easier to retrieve.

Mechanism & reason

The prompt asks for coverage-review before a determination and query_policy for the underlying facts. Procedure ingestion and retrieval have their own domain modules and version records.

Risk & safeguards

A stale procedure can direct an incomplete investigation, while a current procedure can still be combined with the wrong policy revision. Both source identities need to be visible in evaluation and operational diagnosis.

Choice & trade-offs

Separating reasoning guidance from factual material supports independent review but adds retrieval calls and version combinations. Hardcoding all instructions in one prompt is easier to start and harder to govern.

QUESTION 147Insurance code & design analysis#

147. Where does eventual consistency appear to a policyholder?

Read / reveal answer

A claim can be durably submitted before its embedding job completes, so exact structured lookup and semantic search may temporarily disagree. Notification delivery can also lag the claim transaction. These are different read and delivery projections of one business operation.

Mechanism & reason

Submission creates a claim plus pending embedding work in one transaction. Workers later process indexing and notification tasks. The UI should distinguish accepted, searchable, and notified rather than treating one successful HTTP response as completion of every downstream effect.

Risk & safeguards

A search miss immediately after filing must not be reported as proof that no claim exists. An authoritative exact lookup can confirm persistence while the index catches up.

Choice & trade-offs

Asynchronous processing keeps submission independent of provider latency but introduces lag and recovery work. Synchronous indexing is simpler conceptually and couples business availability to model services.

QUESTION 148Insurance code & design analysis#

148. What are the main trust boundaries in this application?

Read / reveal answer

Boundaries include browser-to-API identity, model-to-tool authority, source-to-prompt content, application-to-database privileges, application-to-model disclosure, and application-to-observability export. Each boundary has a different actor and failure mode.

Mechanism & reason

JWT validation establishes a user, ContextVar carries that identity to tools, domain queries constrain records, and tracing can export execution data. Authorization must remain effective even when the model selects the wrong action.

Risk & safeguards

A protected chat endpoint is insufficient if a tool trusts model-supplied owner IDs or a trace exports private claim text. Read and write paths require separate evidence of enforcement.

Choice & trade-offs

Explicit boundaries add policy and testing effort but make failures diagnosable. Combining all access behind a powerful agent credential simplifies integration and magnifies mistakes.

QUESTION 149Insurance code & design analysis#

149. Which application guarantees are implemented, and which remain conditional?

Read / reveal answer

Implemented mechanisms include owner-scoped claims retrieval, a locked confirmation row, caller-owned submission transactions, typed streaming events, optional shared idempotency, and trace instrumentation. Their deployment guarantees depend on real database behavior, chosen storage settings, provider configuration, and complete use of the intended paths.

Mechanism & reason

Configuration defaults session_storage to memory; a database-backed service exists but is not automatically selected in every deployment. Administrative claim transitions also use a currently empty allowlist despite the broader role-support code.

Risk & safeguards

Reading a comment about deployment defaults or a role model as proof of configured behavior creates false confidence. Follow defaults and call sites rather than naming available classes.

Choice & trade-offs

Conservative defaults support local development but may require production gates. Rejecting startup on missing critical state is stricter than silently falling back to local state.

QUESTION 150Insurance code & design analysis#

150. How should the first fourteen chapters be reinterpreted against this host?

Read / reveal answer

Their library concepts remain useful, but each host guarantee needs its own wiring proof. Generic strict retrieval does not mean this host preserves errors, a revision-aware evidence type does not mean policy citations include revisions, and a generic outbox protocol does not prove the concrete adapter's claim semantics.

Mechanism & reason

The coverage audit maps every original question to an insurance extension while preserving Q1–140 and saved progress. The new source atlas pins both repositories so readers can compare capabilities with their actual integration.

Risk & safeguards

Architectural diagrams can accidentally describe an ideal composition rather than the running path. The new diagrams label proposed integrations and the handbook records observed gaps beside the relevant mechanism.

Choice & trade-offs

Cross-project tracing takes more effort than a single overview but teaches integration judgment, the central skill in full-stack AI engineering.
