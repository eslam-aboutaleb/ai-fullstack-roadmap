Understand the topic

UNDERSTAND / 01#

Why can't every network chunk be parsed as JSON?

Read the explanation

A read can contain half a character, half an event, or several events. First decode text incrementally, then frame SSE messages, then parse each completed payload.

These layers have different boundaries.

A CONCRETE EXAMPLE

One read ends at da and the next begins ta:. Neither is a complete SSE field on its own.

Keep this idea: Transport chunks are not application messages.

UNDERSTAND / 02#

What ends an SSE event?

Read the explanation

A blank line ends an event under SSE framing rules. Multiple data fields combine into the event's data value; comments and other fields have their own meaning.

Handle line endings and partial final input deliberately.

A CONCRETE EXAMPLE

Two data lines are one event with a newline between their values, not two independently dispatched answers.

Keep this idea: Decode framing before interpreting business content.

UNDERSTAND / 03#

When should you use EventSource versus fetch?

Read the explanation

EventSource supports the browser's SSE connection behavior over GET, but not arbitrary custom headers. Fetch provides method and header control while leaving parsing and reconnect policy to your application.

Choose from your authentication and replay contract.

A CONCRETE EXAMPLE

A bearer-header flow can use fetch streaming; a suitable cookie-authenticated GET flow may use EventSource.

Keep this idea: The convenient client must fit the credential model.

UNDERSTAND / 04#

How does replay avoid duplicate text?

Read the explanation

Use ordered event IDs and a declared retention policy. Resume after the last processed ID and deduplicate repeats.

If history expired, return an explicit snapshot or resume failure instead of silently skipping content.

A CONCRETE EXAMPLE

Replaying event seven should not append its text twice after reconnect.

Keep this idea: Reconnection needs application-level state semantics.

UNDERSTAND / 05#

Why can a correct local stream arrive in bursts in production?

Read the explanation

Proxies or platforms may buffer output or close idle connections. Configure supported streaming behavior and measure actual browser arrival times through the deployed path.

Heartbeats help idle connections but do not prove the application is progressing.

A CONCRETE EXAMPLE

The server writes every 100 milliseconds while the proxy forwards once per second. The model is not the bottleneck.

Keep this idea: Measure end-to-end delivery rather than server writes alone.

UNDERSTAND / 06#

How do cancellation and completion differ?

Read the explanation

Disconnect can stop generation or leave durable work running according to policy. A final completion event should reference the recorded result.

Neither a closed socket nor the model's final token proves that a business action finished.

A CONCRETE EXAMPLE

The browser disconnects after commit; the result endpoint still returns the completed operation.

Keep this idea: Task state must survive transport ambiguity when the product requires it.

FROM IDEA TO CODE

Read a small implementation

Standard library: incremental UTF-8 SSE parser with multiline data and CR/LF handling. JSON validation is separate.

What this demonstrates: Understand one-way server events byte by byte.

Connect it to the case: A Unicode answer arrives across several network reads. The browser reconstructs each complete event before parsing its JSON data.

import codecs

def parse_sse(chunks):
    decoder = codecs.getincrementaldecoder("utf-8-sig")()
    line, data, kind, last_id, skip_lf, events = "", [], "", "", False, []
    def consume_line(value):
        nonlocal data, kind, last_id
        if value == "":
            if data:
                events.append({"event": kind or "message", "id": last_id,
                               "data": "\n".join(data)})
            data, kind = [], ""
            return
        if value.startswith(":"): return
        field, sep, text = value.partition(":")
        if text.startswith(" "): text = text[1:]
        if field == "data":
            data.append(text)
            if sum(map(len, data)) > 1_000_000: raise ValueError("event too large")
        elif field == "event": kind = text
        elif field == "id" and "\x00" not in text: last_id = text
        # retry and unknown fields are intentionally not acted on by this decoder.
    for chunk in chunks:
        for char in decoder.decode(chunk):
            if skip_lf:
                skip_lf = False
                if char == "\n": continue
            if char in "\r\n":
                consume_line(line)
                line = ""
                skip_lf = char == "\r"
            else:
                line += char
                if len(line) > 65536: raise ValueError("line too large")
    decoder.decode(b"", final=True)  # Reject truncated UTF-8; do not dispatch partial events.
    return events

raw = "id: 1\r\nevent: delta\r\ndata: Héllo\r\ndata: world\r\n\r\n".encode()
for split in range(len(raw) + 1):
    assert parse_sse([raw[:split], raw[split:]])[0]["data"] == "Héllo\nworld"
How to read and test this code
  1. The incremental decoder handles characters split across byte chunks.
  2. The parser accumulates lines and dispatches data only at an event boundary.
  3. The final loop tries every split of one Unicode fixture; retry policy and JSON validation remain separate.

When should an AI application use SSE?

Server-Sent Events suit a server-to-browser stream of text or task progress over HTTP. Use a separate request to submit work or cancel a task when bidirectional messaging is unnecessary.

How this works

Define a stable event schema and stream the safe projection of run state. SSE is a transport for events, not a durable task engine.

What could go wrong?

An open connection does not prove that work is persisted or authorized.

Why choose this approach?

SSE fits HTTP infrastructure and offers only one-way messaging on that connection.

How is an SSE message framed?

An event consists of text fields followed by a blank line. Data may span multiple data lines, which the receiver combines according to SSE rules.

Network chunks do not align with event boundaries.

How this works

Decode UTF-8 incrementally, accumulate lines, and dispatch only at the event delimiter. Normalize supported line endings and impose limits.

What could go wrong?

Parsing each received chunk as JSON fails when characters or messages split across chunks.

Why choose this approach?

Correct incremental parsing adds state and avoids intermittent corruption.

How should EventSource and fetch streaming be compared?

Browser EventSource handles an SSE GET connection and reconnection behavior. Fetch streaming gives control over methods, headers, and request bodies but requires application parsing and retry logic.

How this works

Choose based on authentication, request semantics, and resume requirements. Do not assume EventSource accepts arbitrary authorization headers.

What could go wrong?

Putting bearer tokens in query parameters can expose them in logs and history.

Why choose this approach?

Fetch offers flexibility while EventSource supplies useful protocol behavior.

Try it yourself

Design a cookie-authenticated EventSource flow and a header-authenticated fetch flow.

What should a public AI event schema contain?

Include schema version, task ID, ordered sequence, event type, and typed payload. Distinguish text deltas, tool activity, final results, recoverable notices, and terminal errors.

How this works

Convert provider events through an adapter. The UI should reduce these events into explicit states rather than concatenate every payload into answer text.

What could go wrong?

Provider-internal messages can leak private arguments or confuse partial output with completion.

Why choose this approach?

Stable schemas add adapter maintenance and protect the UI from provider churn.

How should reconnection and replay work?

Give events durable sequence IDs and define a retention window. Resume from the last acknowledged or processed event, and deduplicate repeated sequence numbers.

How this works

If replay history expired, return a snapshot or a clear resume failure. Revalidate ownership on every connection.

What could go wrong?

Reconnecting without a replay contract can lose events or duplicate displayed text.

Why choose this approach?

Durable event storage adds cost and enables recovery.

How do heartbeats and proxy buffering affect streams?

Intermediaries may buffer output or close idle connections. Heartbeats can keep an otherwise idle stream active, but infrastructure behavior must be measured.

How this works

Use appropriate content type and cache policy, disable buffering where supported, and send bounded periodic comments. Check actual arrival times through the production proxy.

What could go wrong?

Application flushes alone do not establish that the browser receives each event promptly.

Why choose this approach?

Frequent heartbeats consume connections and bandwidth.

How should cancellation work with SSE?

Closing a stream should stop unnecessary generation according to product policy, while durable tasks may continue independently. Expose a task cancellation endpoint for explicit control.

How this works

Propagate cancellation to providers when supported and record the final task state. Preserve committed operation IDs for later lookup.

What could go wrong?

A disconnected stream does not prove that external effects were cancelled.

Why choose this approach?

Separating task and stream lifetimes adds complexity and enables background completion.

Try it yourself

How should backpressure be handled?

Bound producer-to-writer queues and prevent slow clients from retaining unlimited memory. Decide which progress events can be coalesced and which terminal events must be retained.

How this works

Await writable capacity where the framework supports it, monitor queue depth, and disconnect consumers that cannot keep up under the contract.

What could go wrong?

Dropping arbitrary text deltas corrupts the answer.

Why choose this approach?

Strong limits may disconnect slow clients and protect the server.

What should completion mean in an SSE stream?

A completion event should identify the persisted result or authoritative final task state. A finished model token sequence is not necessarily a completed application operation.

How this works

Persist the final record before emitting completion and support owner-scoped result retrieval after disconnect.

What could go wrong?

A crash after sending done but before commit creates a false success.

Why choose this approach?

Persist-before-complete adds final latency and strengthens recovery.

Try it yourself

Crash at the completion boundary and verify the UI can recover from the result endpoint.

How should SSE be tested?

Test UTF-8 boundaries, multiline data, line endings, comments, empty data, malformed payloads, replay, authorization, disconnects, and slow consumers. Test through the real proxy as well as in process.

How this works

Keep transport decoding separate from JSON schema validation and UI reduction. Assert both event order and terminal state.

What could go wrong?

A happy-path mock stream misses buffering and network fragmentation.

Why choose this approach?

Real transport tests cost more and catch difficult intermittent failures.
