# AI full-stack engineering coverage audit

Current chapter ordering and inventory are recorded in the [learning journey review](learning-journey-review.md). This report describes the preceding enrichment pass.

Reviewed 20 October 2026 against the merged 48-chapter, seven-track manifest, the two structured foundation courses, the 13 assessment records, four browser labs and four downloadable capstones. The live result for all catalogued references is in [reference-link-audit.md](reference-link-audit.md); machine-readable status codes, final URLs, page titles and source usages are in [reference-link-audit.json](reference-link-audit.json).

A subsequent implementation pass adds six courses with 32 units and repairs existing interview context. See [content-enrichment-review.md](content-enrichment-review.md) for current authored material and remaining limits. The matrix below records the audit baseline that motivated that work.

## Overall finding

The roadmap has a wide topic inventory. Inventory coverage and course mastery are different: the manifest currently assigns 15 of 48 chapters to agents, 10 to AI/RAG, eight to backend/data, four to Python/CS, four to operations, four to system design and three to frontend. Yet only three chapters have the full enriched lesson schema, 40 of 480 interview records have the enriched answer fields, and the two new structured courses contain 15 units total. Several deep topics therefore appear as a chapter title, questions, concise explanation or vendor-framework comparison instead of a prerequisite-driven sequence of taught concepts, cumulative exercises and verified projects.

This is a content-coverage judgment, not a claim that omitted terms never appear in a legacy answer. See the source-backed chapter and reference matrix before making those judgments. The roadmap should label a topic “introduced”, “practiced” or “independently demonstrated” based on instructional evidence, not solely on its presence in the DAG.

The 56 original reference destinations all returned HTTP 200. Exact source tracing found `ls-observability` in the catalog without a use in any lesson; that source is now attached to the agent observability chapter. The two MCP links used a November 2025 specification path even though the protocol site now serves a July 2026 edition. Those chapter references have been advanced to the current edition. The catalog also lacked primary references for React, TypeScript, API/security standards, data-stream processing, deployment infrastructure, ANN and subword tokenization; verified official documentation and papers have been added to the corresponding chapter source lists. Each live result is rerun into the linked audit when `python3 scripts/audit_references.py` is run.

## Recommended authoring sequence

1. Establish stable outcome IDs and cross-track prerequisites. Decide which chapters are course modules and which are reference/interview banks. Add explicit prerequisites and baseline level so the AI-specific content does not assume a full CS/web/data curriculum without saying so.
2. Expand the foundations path first: programming/Python/CS, web/TypeScript/React, math/classical ML, SQL and data engineering. Reuse the existing seven and eight course units as seeds, then write substantial lessons with worked and unworked examples.
3. Rebuild LLM/API and RAG material as a cumulative end-to-end course. Add missing provider, retrieval and security references to specific lessons. Keep fixture outputs deterministic and include a local/mock route for every hosted-model example.
4. Sequence agents, MCP/A2A, security and operations after the learner can build and observe a normal service. Treat framework chapters as comparisons that exercise shared concepts.
5. Complete capstones with starter/reference code, objective tests, failure injection, measured resource budgets, rubrics and expected artifacts. Add negative cases and trace-level assessment before increasing the question-bank size.
6. Review in small release batches. Require a named technical reviewer, dated notes and content hash for each reviewed item; separately review references, runnable examples, accessibility and diagram alternatives. Show draft versus reviewed counts accurately.

## Reference-quality findings to apply

- Prefer standards, papers and language/framework maintainer documentation for general claims. Product evaluation pages are useful examples, not neutral ground truth; compare their metric definitions and failure modes.
- Keep versioned protocol references fixed to a protocol edition where the lesson depends on it. For `/latest/` and `/current/` documentation, record the date/version checked and state when behavior is version-sensitive.
- Cite references at the claim or lesson where they support the explanation. A global source catalog entry that no lesson uses is not evidence that topic is taught.
- The new references improve traceability but do not fill the teaching gaps by themselves. In particular, add worked cost/latency capacity models, deeper data-schema evolution/lineage instruction, and a complete provider-neutral LLM application module with reproducible local exercises. Provider specific OpenAI and Gemini references currently sit with the full-stack integration chapter; compare their contracts and teach the portable interface separately.
