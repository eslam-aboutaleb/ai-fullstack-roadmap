Understand the topic

UNDERSTAND / 01#

Which steps may run in parallel?

Read the explanation

Only steps whose required inputs and authority are already established. A later step needing an earlier result is a dependency, not an opportunity for concurrency.

Bound parallelism according to downstream capacity.

A CONCRETE EXAMPLE

Search three corpora concurrently, then assemble the combined evidence; do not execute a write while its validation is still running.

Keep this idea: Parallelize independent work, not unresolved assumptions.

UNDERSTAND / 02#

How should fan-in treat one failed branch?

Read the explanation

Define whether the task requires all results or can proceed with explicitly limited coverage. Preserve each branch's outcome and provenance so a partial answer is not presented as complete.

A CONCRETE EXAMPLE

Two knowledge sources succeed and the authoritative exception source times out. The answer must not ignore that missing authority.

Keep this idea: Partial success needs task-specific semantics.

UNDERSTAND / 03#

What state must survive a crash?

Read the explanation

Preserve the task goal, principal reference, completed operation IDs, pending dependencies, budget, approval requirements, and terminal status. Keep model plans separate from authoritative completed effects.

A CONCRETE EXAMPLE

On restart, use the operation ledger to discover that a previously pending write already committed.

Keep this idea: Durable orchestration refers to durable business outcomes.

UNDERSTAND / 04#

How should retries be coordinated?

Read the explanation

Classify the failure, preserve the operation key, and count every attempt in the same task deadline and budget. Retry transient reads differently from uncertain writes.

Query status when completion is ambiguous.

A CONCRETE EXAMPLE

A payment timeout may mean committed but response lost. Starting a new payment is not a safe generic retry.

Keep this idea: Recovery must reflect what may already have happened.

UNDERSTAND / 05#

How should a workflow pause for human approval?

Read the explanation

Persist a review requirement bound to exact parameters and revision. Resume only after authenticating the approving actor and rechecking current state.

A waiting graph node or yes message is not sufficient proof.

A CONCRETE EXAMPLE

A changed amount invalidates the old approval even if the workflow is still at the same visual step.

Keep this idea: Approval is data with authority, scope, and expiry.

FROM IDEA TO CODE

Read a small implementation

python

Standard library: bounded parallel read tasks; no external services.

What this demonstrates: Coordinate dependent and parallel work without losing ownership.

Connect it to the case: Search three permitted corpora while a separate approval step waits. Independent reads can run together; the write cannot start before review.

import asyncio
async def gather_sources(searchers, query, concurrency=2):
    semaphore = asyncio.Semaphore(concurrency)
    async def one(name, search):
        async with semaphore:
            try:
                return {"source": name, "status": "ok", "items": await search(query)}
            except (TimeoutError, OSError):
                return {"source": name, "status": "unavailable", "items": []}
    return await asyncio.gather(*(one(name, fn) for name, fn in searchers.items()))
async def demo():
    async def local(query): return ["synthetic passage"]
    assert (await gather_sources({"demo": local}, "hours"))[0]["status"] == "ok"
if __name__ == "__main__": asyncio.run(demo())
# Add deadlines, shared quotas, and task persistence around real services.
How to read and test this code
  1. Each source search acquires the same local semaphore.
  2. gather combines per-source outcomes instead of silently dropping a failed branch.
  3. Add task deadlines and fleet quotas; local concurrency is not total deployment capacity.

When is a fixed workflow better than an autonomous agent?

Prefer a fixed workflow when the valid sequence is known and business rules dominate. Use an agent where choosing among tools or exploring uncertain evidence adds measurable value.

How this works

Put deterministic validation and writes in application services. Limit model discretion to decisions that benefit from language understanding or flexible planning.

What could go wrong?

An autonomous loop can add latency and unpredictable paths to an otherwise simple operation.

Why choose this approach?

Fixed flows are easier to verify and less adaptable to unexpected tasks.

How should orchestration state be modeled?

Represent goal, principal reference, completed steps, pending actions, evidence IDs, budget, and terminal status explicitly. Keep durable operation outcomes separate from model-generated plans.

How this works

Use typed transitions and immutable identifiers. Persist checkpoints at recoverable boundaries and validate loaded state before resuming.

What could go wrong?

A checkpoint can be stale relative to the business database.

Why choose this approach?

Explicit state adds modeling work and makes restart behavior understandable.

Try it yourself

Resume after a crash between a completed tool call and the next model call.

What is fan-out and fan-in orchestration?

Fan-out runs independent tasks concurrently; fan-in combines their results under a declared policy. Parallel execution is useful only when tasks do not require each other's outputs.

How this works

Bound concurrency and define whether aggregation requires all results, a quorum, or best-effort partial output. Preserve per-branch errors and provenance.

What could go wrong?

One slow branch can delay completion or cause unbounded task growth.

Why choose this approach?

Parallelism reduces latency and raises peak load and coordination cost.

Try it yourself

How should dependencies be represented?

Use a directed dependency graph when tasks require earlier outputs. Validate that the graph is acyclic unless a bounded loop has deliberate semantics.

How this works

Execute ready nodes, propagate typed outputs, and make failure handling explicit per edge. A task plan does not establish permission.

What could go wrong?

Incorrect dependency declarations can execute a write before validation.

Why choose this approach?

Graphs improve visibility while increasing orchestration machinery.

Try it yourself

Model extract, validate, review, and submit with a required approval edge.

How does durable execution differ from retrying the whole agent?

Durable execution resumes from recorded progress instead of blindly repeating every prior action. It requires deliberate handling of nondeterministic work and external side effects.

How this works

Persist operation keys and results, and make repeated execution safe at each resumable boundary. Checkpoint behavior depends on the runtime and version.

What could go wrong?

Replaying a node can duplicate a write if the business operation is not idempotent.

Why choose this approach?

Durability adds storage and state evolution work.

Try it yourself

Demonstrate a crash after external execution but before checkpoint persistence.

What should an orchestrator do when one tool fails?

Classify failure by cause and effect: invalid input, denied access, transient outage, uncertain completion, or terminal business rejection. Select retry, clarification, status lookup, fallback, or escalation accordingly.

How this works

Apply a remaining-deadline budget and preserve the original operation ID across uncertain retries.

What could go wrong?

Treating every exception as retryable can multiply writes or provider load.

Why choose this approach?

Detailed policies require maintenance and avoid broad unsafe retries.

Try it yourself

Write a failure table with an allowed recovery action for each category.

How should human approval be represented in a workflow?

Approval is a server-verified event bound to a specific principal, operation, parameters, expiry, and revision. A waiting workflow state should reference that approval requirement.

How this works

Resume only after checking the approval and current business state. Reject stale approvals after material parameter changes.

What could go wrong?

A graph interrupt or chat message is not an authorization proof.

Why choose this approach?

Explicit approvals add latency and auditability.

Try it yourself

Modify an approved operation and verify that the workflow returns to review.

How should shared memory work across multiple agents?

Share only scoped facts and artifacts that each participant needs. Use a coordinator-owned task record and explicit output contracts instead of a writable universal scratchpad.

How this works

Track who produced each fact and which service can verify it. Merge conflicts through rules rather than last-writer-wins prose.

What could go wrong?

One agent's unsupported assumption can spread to all others.

Why choose this approach?

Restricted sharing reduces context reuse and limits error propagation.

Try it yourself

Have two agents disagree on a version and require evidence-based reconciliation.

Write my explanation

How do you prevent orchestration cost explosions?

Bound total model calls, tool calls, elapsed time, parallel tasks, and spend per user task. Include retries and critic loops in the same budget.

How this works

Stop at an explicit terminal state and explain incomplete work using recorded outcomes. Apply fleet-level quotas in addition to local semaphores.

What could go wrong?

Nested agents can each obey a local limit while exceeding the parent task budget.

Why choose this approach?

Tight budgets reduce task coverage and control operational risk.

Try it yourself

Build a parent budget that every child operation must reserve before execution.

How should orchestration be evaluated?

Measure end-to-end outcomes, permission invariants, valid state transitions, recovery behavior, latency, and total task cost. Inspect trajectories to explain failures.

How this works

Use deterministic replay where possible, sandbox external effects, and inject crashes at durable boundaries.

What could go wrong?

Matching one reference sequence can reject alternative valid solutions.

Why choose this approach?

Invariant-based evaluation accepts valid diversity and requires thoughtful specifications.

Try it yourself

Evaluate two different successful tool sequences against the same business invariants.
