SIX STAGES / 48 PRACTICAL LABS

Learn by building.
Prove it by breaking it.

Complete each stage with a small implementation, a failure demonstration, and a clear explanation. The path is flexible: use your actual gaps to choose depth.

One fictional capstone throughout

Build a multi-tenant support platform with versioned knowledge, customer-owned service requests, approved business actions, and a recoverable task lifecycle. Start text-only. Add voice and document processing when their chapters become relevant.

Suggested sequence: backend and data → retrieval and evidence → agent tools → context and prompts → MCP and skills → durable orchestration → evaluation → streaming and multimodal delivery.

STAGE 1

RAG and engineering foundations

LAB 01

RAG foundations

Build the mental model before choosing infrastructure.

  1. Trace one document through ingestion and one question through search. Draw the boundary where your own generator must be called.
  2. Annotate a sample result with its source ID, document ID, revision, chunk ID, text, vector dimension, and evidence label. Identify which fields can change after reindexing.
  3. Compare an HR policy assistant and a public FAQ assistant. List five knowledge rules that differ even if they use identical the retrieval service components.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Confusing a chunk ID with a document ID breaks deletion, citation lookup, and version switching. the retrieval service carries metadata through the pipeline, but hosts must supply stable source identities and meaningful provenance.
  • Defend this trade-off with a baseline or a documented constraint: Reusability reduces coupling but requires deliberate integration work. A specialized application may be quicker initially and harder to reuse safely later.
Solution outline

Separate the offline path, which builds a searchable corpus, from the online path, which retrieves evidence for a question. This lets a source change trigger indexing without retraining the language model. The original RAG paper combines parametric model memory with a retrieved non-parametric index; this reference design is an engineering subsystem, not a reproduction of that training architecture.

The canonical Chunk, Document, and SearchResult dataclasses separate ingestion and search shapes; evidence types add revision, source, span, and citation information. A chunk hit becomes useful evidence only after selection and attribution.

LAB 02

Architecture and design patterns

Understand the dependency boundaries and why each seam exists.

  1. Draw a ports-and-adapters diagram showing which side owns users, SQL tables, provider credentials, evidence, and chat responses.
  2. Explain how adding a new vector backend differs from adding a query reranker. Identify the construction, contract, and behavior changes separately.
  3. Prepare a five-minute defense with three source references, two explicit limitations, and one alternative architecture you would choose under different requirements.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: A name-based registry can defer typos or missing optional dependency failures until runtime. Validate names and dependencies during startup, and avoid loading plugins based on arbitrary untrusted input.
  • Defend this trade-off with a baseline or a documented constraint: Qualified service requests sound less absolute but survive technical scrutiny. A good design defense acknowledges obligations pushed to host adapters and conditions under which another design would win.
Solution outline

Expose retrieval, ingestion, and evidence contracts independently from web routes and business models. The host binds authentication, persistence, and generation policy. This makes components testable without implying that every backend is interchangeable.

Store factories and registries choose backend implementations; retrieval strategies compose search capabilities; backend classes translate vendor operations. This allows configuration-driven construction without forcing every search behavior into a storage class.

LAB 03

Sources, connectors, and extraction

Reliable knowledge starts with knowing what was actually scanned.

  1. Trace a PDF in an object bucket through all four stages. Specify the returned status when each stage fails and which stages can be retried independently.
  2. Inspect the checks before and after a redirect. Explain why allowing example.com does not authorize a redirect to a loopback address.
  3. Stop the watcher, edit and delete files, then resume it. Describe how a scheduled reconciliation repairs changes that the live event stream never delivered.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Domain checking alone cannot stop DNS rebinding or redirect-based bypasses. Egress policy, deployment DNS behavior, and the actual client transport also matter. Treat source fetching as a separate trust boundary.
  • Defend this trade-off with a baseline or a documented constraint: Combining watchers with scans spends extra source I/O but improves eventual correctness. Full scans alone are simpler when freshness requirements are modest.
Solution outline

Connector records carry discovery and load status, while a source-document record carries content and source metadata into the pipeline. A PDF extraction failure is therefore different from an empty bucket or an embedding provider outage.

The HTTP connector validates destinations, pins requests to an approved public IP, disables automatic redirects, and checks redirects explicitly. It rejects attempts to turn off its network protections. Website crawling requires explicit allowed domains.

LAB 04

Chunking and document structure

Treat chunking as an information boundary, not a magic constant.

  1. Split the same policy into small and large chunks. Use questions about exceptions and compare whether each retrieved unit contains enough information to answer safely.
  2. Use a document with a preamble, H2 sections, H3 headings, and a fenced code sample containing a heading-like line. Inspect the exact emitted chunk text.
  3. Compare three sizes with two overlaps and publish a table containing quality, indexed chunk count, and estimated embedding input. Explain the winning configuration's remaining failure cases.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: A regular expression for H2 headings is not a complete Markdown parser. Unusual markup and headings inside fenced code can create misleading boundaries. Evaluate actual corpus syntax before relying on section semantics.
  • Defend this trade-off with a baseline or a documented constraint: A full grid search costs indexing time. Start with a small set of plausible configurations and investigate failure examples before expanding the search.
Solution outline

The retrieval service injects a Chunker into ingestion. This makes chunking a replaceable strategy whose version and configuration participate in snapshot comparison, rather than an untracked preprocessing script.

Composition reuses the sliding-window algorithm while adding section, chunk index, and sub-chunk index metadata. File reading remains in the source adapter; the chunker operates on text.

LAB 05

Embeddings and resilient execution

Protect vector compatibility, provider capacity, and tenant data.

  1. Define two profiles with the same dimension and different models. Explain why a successful database insert would not prove they can share one search space.
  2. Simulate two transient failures followed by success, then a permanent failure. Record attempts and delays using injected clock and sleep functions.
  3. Compare a cold ingestion with an unchanged-source rerun and a model-change rerun. Attribute work saved by snapshot skipping separately from cache hits.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Classification includes message-pattern heuristics and treats unknown errors as transient. Misclassification can waste calls, and Retry-After can extend operation duration. The host still needs an overall deadline and provider-specific error handling where necessary.
  • Defend this trade-off with a baseline or a documented constraint: Detailed metrics improve tuning while high-cardinality labels and raw text logging create overhead and privacy risks. Prefer aggregated, sanitized dimensions.
Solution outline

An embedding profile records provider, endpoint, model, revision, dimension, normalization, metric, task mode, and preprocessing configuration. Its canonical hash gives the indexing configuration a stable identity that can be carried into snapshots and caches.

A bounded embedding executor classifies exceptions, honors exposed Retry-After hints, applies a retry ceiling, and validates responses. Cancellation is propagated rather than treated as another retryable failure.

LAB 06

Vector storage and database design

Choose guarantees as carefully as similarity algorithms.

  1. Create a decision matrix for persistence, filters, lexical search, transactions, generation visibility, and deletion latency for two candidate backends.
  2. Compare a malicious value, a malicious table name, and a syntactically valid but unauthorized table name. Explain which layer must stop each one.
  3. Build an adapter that rejects range filters and transactions. Send requests requiring each feature and verify rejection occurs before any evidence is returned.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: A valid identifier is not proof of authorization to access that table. Hosts must select trusted schema configuration and limit database permissions. Application transport validation also remains necessary.
  • Defend this trade-off with a baseline or a documented constraint: Fail-closed behavior reduces surprising leakage but can reject configurations that previously appeared to work. That incompatibility is useful when the earlier behavior was unsafe or incomplete.
Solution outline

The retrieval service's store contracts combine or separate writing, vector search, lexical search, fetch, and deletion. Backend capability declarations describe which operations and constraints the adapter actually supports.

The validation helper restricts identifiers to a simple allowlisted syntax. the PostgreSQL vector adapter applies validation when constructing operations and keeps values in parameter dictionaries. This is safer than escaping arbitrary user-provided SQL fragments.

LAB 07

Retrieval, fusion, and reranking

Find candidates, enforce constraints, then spend ranking effort wisely.

  1. Construct one request for tenant A with a larger candidate pool and a smaller final result set. Explain every field that affects authorization, ranking, or visibility.
  2. Inspect ten candidates with similar vocabulary but different policy conditions. Compare fused ordering with reranked ordering and classify whether improvement justifies added cost.
  3. Create a failure report containing the first stage where an expected passage disappears, the supporting observation, and one focused change to test.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: External reranking may transmit document content to another provider, add latency, or fail. Authorization and data-handling policy must apply before transmission, and timeout or failure behavior should be explicit.
  • Defend this trade-off with a baseline or a documented constraint: Stage-by-stage diagnosis takes longer than tweaking a single constant but targets the actual cause and prevents compensating errors.
Solution outline

A hybrid retriever coerces legacy calls into this form and validates supported constraints before delegating to a store or strategy. Effective filters and required metadata help preserve scope checks across the execution path.

Hybrid retrieval accepts an optional Reranker protocol. a model-backed reranker is one adapter, while a host can supply another implementation. Typed responses preserve richer score information where required.

LAB 08

Evidence, context, and citations

Turn ranked hits into bounded material a person can verify.

  1. Feed duplicate and overlapping hits from two sources into the assembler. Inspect both selected text and the counters explaining what was removed or merged.
  2. Give one source eight high-ranked chunks and another one relevant chunk. Compare evidence selection with the product's expected authority policy.
  3. Draft a generation policy for answerable, ambiguous, empty, stale, and failed retrieval cases. Create one acceptance example for each branch.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Diversity may demote the only authoritative source in favor of weaker material. Source quality and authority are product knowledge rules that may need explicit weighting or filtering outside the default heuristic.
  • Defend this trade-off with a baseline or a documented constraint: Strict evidence-only answering improves traceability but can feel less helpful for general questions. Clearly separated modes can preserve user expectations.
Solution outline

An evidence assembler coerces supported hit shapes, deduplicates, merges eligible spans, balances source diversity, selects items, and renders stable citation labels. This deterministic layer can be tested independently of an unpredictable generator.

The assembler ranks within sources and interleaves them before budget selection. This can preserve diversity even when a long source produces many high-scoring chunks.

LAB 09

Ingestion and transaction ownership

Keep expensive preparation outside the critical mutation window.

  1. Instrument session entry, embedding start, lock acquisition, upsert, and commit. Compare internally owned and caller-owned session paths.
  2. Add an unrelated host row before calling ingestion with the same session. Roll back and verify whether both mutations obey the host's intended transaction.
  3. Benchmark the critical section across increasing chunk counts. Report distributions and test conditions, and keep provider time separate from database time.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: A host that forgets to commit loses intended changes; a host that keeps the transaction open across slow preparation can retain connections and locks too long. Session ownership must be clear at integration boundaries.
  • Defend this trade-off with a baseline or a documented constraint: Shorter transactions reduce contention but preparation may still dominate end-to-end ingestion time. Optimization should target measured bottlenecks without weakening atomicity.
Solution outline

Slow provider work precedes the mutation-critical section. This reduces the time an internally owned session and advisory lock are held for version changes. The read-only initial snapshot check uses a short session when the caller did not supply one.

_transacting_session implements the distinction and can acquire the advisory lock on a caller session when a lock key is supplied. The lock lifetime still follows the actual database and transaction behavior.

LAB 10

Distributed sync, jobs, and recovery

Reason about stale workers and partial writes using explicit state.

  1. Compare the state required to replace one file with the state required to sync a million-object collection across two workers and intermittent source failures.
  2. Make one of three documents fail embedding. Compare reports and visible generations in both modes and state which behavior your product requires.
  3. Build a crash matrix for preparation, vector write, manifest activation, checkpoint, and cleanup. For each point identify visible state and the next repair action.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Cross-store atomicity is not created automatically by selecting collection mode. Durable adapters must preserve the fenced and batch visibility obligations, including failure between manifest commit and generation advancement.
  • Defend this trade-off with a baseline or a documented constraint: Conservative cleanup leaves temporary storage overhead while protecting visible data. Aggressive deletion reduces space and can make recovery unsafe.
Solution outline

A sync coordinator composes source scans, manifests, fencing state, embeddings, vector storage, optional reconciliation jobs, and garbage collection. It prepares generations before committing visibility through manifests.

The coordinator's preparation loop records errors; collection mode raises on preparation failure, while document mode can continue. The activation path updates manifests and collection state under the supplied coordination contracts.

LAB 11

Security, tools, and trust boundaries

Connect identities to scopes before exposing knowledge to users or agents.

  1. Draw an API request with identity, requested collection, and requested scope. Mark which values are trusted and where each becomes constrained.
  2. Define reader, operator, and administrator roles. Map each to search, source lookup, sync, and revocation, then state where the host enforces each permission.
  3. Write five adversarial scenarios with expected denial and one authorized control case for each. Specify whether denial must occur before any external provider receives document text.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Enabling a management tool globally without per-caller policy can give an agent excessive authority. Source text must never grant that authority by instructing the model to call a privileged tool.
  • Defend this trade-off with a baseline or a documented constraint: Boundary tests take setup but prevent high-impact failures. Duplicating every implementation branch with brittle tests is less valuable than exercising the invariants users depend on.
Solution outline

The tool bridge composes scope authorization with retrieval and source lookup. MCP identity can come from trusted transport context or a host callback rather than a model-supplied client identifier.

The MCP server defaults to read tools, while management registration and the bridge's allow_management setting provide separate opt-in controls. Those controls complement, rather than replace, identity-based authorization.

Evaluation, testing, and operations

Turn service requests about quality and reliability into repeatable evidence.

  1. For relevant IDs A and B and ranking C,A,D,B, calculate metrics at K=3. Then compare with the harness's exact conventions.
  2. For one transaction guarantee and one retrieval filter guarantee, state which test needs a real database and which can use a controlled fake.
  3. Simulate an unchanged corpus with a changed query mix, then a changed extractor with the old query mix. Show how you would distinguish the resulting metric changes.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Passing fake-based tests cannot prove production rollback, SQL locking, or vendor filter behavior. Conversely, an enormous end-to-end suite can be slow and poor at locating failures.
  • Defend this trade-off with a baseline or a documented constraint: Stable benchmarks preserve comparability but can become unrepresentative. Add reviewed new cases while keeping a fixed core set for historical comparison.
Solution outline

An evaluation runner evaluates an injected retrieval function against labeled chunk IDs and records latency and errors. Always inspect denominator and short-result handling in the implementation before comparing scores with another tool.

The test suite has targeted modules for ingestion locking, embedding execution, retrieval capabilities, and sync coordination. These boundaries are more consequential than mirroring every helper's internal implementation.

Deep learning and generative AI

Learn the model concepts behind the interfaces without confusing them with implemented features.

  1. Label each reference component as deterministic infrastructure, learned-model adapter, or application boundary. Explain why several components require more than one learning discipline.
  2. Divide twenty failures into missing evidence, bad ranking, bad prompt policy, and persistent behavioral problems. Choose which, if any, justify SFT.
  3. Follow the roadmap labs, then train a tiny contrastive encoder on a reviewed toy dataset. Compare it with the hashing baseline and a pretrained model using the same held-out queries.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Fine-tuning on private facts can create memorization and retention problems without solving freshness or citation. Poor examples can also teach confident unsupported answering.
  • Defend this trade-off with a baseline or a documented constraint: Breadth requires sustained practice. Sequence small, testable projects rather than attempting to master distributed storage and large-model training simultaneously.
Solution outline

The retrieval service can call learned embedding and reranking providers, but much of its code is deterministic orchestration, validation, indexing, and coordination. Understanding that division prevents attributing every system behavior to a neural model.

The reference design does not include a model-training pipeline. Its datasets and answer evaluators support application evaluation, not an automatic SFT trainer. A host can use evaluation failures to decide whether behavior adaptation is warranted.

Acceptance evidence

LAB 17

Transactions, locks, and concurrency

Prove what happens when retries, users, and workers race.

  1. Start two confirmations simultaneously in separate database sessions. Assert one logical claim and one consumed submission, then inspect the losing request's result.
  2. Interleave two workers between selection and marking. Verify the loser receives no processing payload for the contested job.
  3. Specify barriers for two confirmations, two job service requests, and two session-state updates. State the invariant each test could falsify.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: Describing selection alone as exclusive ownership hides a race and encourages unsafe future changes. Completion and reclamation also need ownership-aware conditions to prevent obsolete workers from overwriting newer outcomes.
  • Defend this trade-off with a baseline or a documented constraint: Deterministic integration tests take setup but produce stronger evidence and fewer flaky timing assumptions. Broad stress tests complement them and do not replace them.
Solution outline

Select the pending operation by trusted owner and token, acquire the appropriate row lock, recheck expiry and state, then apply the effect and final state in one transaction.

If candidate selection ends its transaction before acquisition, a later conditional update establishes ownership. Alternatively, claim atomically in one transaction; inspect the whole lifecycle before asserting exclusivity.

Securing database operations

  1. Design a grant matrix for API, embedding worker, notification worker, migrator, and analyst. Include which sensitive tables each must never read.
  2. Propose settings for pool wait, lock wait, and statement time with a measured request budget. Simulate a blocked transaction and observe rollback and connection reuse.

Acceptance evidence

  • Demonstrate the required behavior using synthetic fixtures and record the actual outcome.
  • Reproduce this failure boundary: An expensive permitted query can be a denial-of-service vector. Very short timeouts can also cause retry amplification or repeatedly abort useful work.
  • Defend this trade-off with a baseline or a documented constraint: A capability-oriented service layer takes design work and supports safe reuse across orchestration frameworks. Direct ORM access inside every agent is fast to prototype and hard to govern.
Solution outline

Set connection, statement, lock, and transaction-duration limits according to workload. Cancel abandoned work and keep application deadlines shorter than an uncontrolled sequence of downstream waits.

LAB 23
