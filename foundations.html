Understand the topic

UNDERSTAND / 01#

What problem does RAG solve before we discuss any architecture?

Read the explanation

Imagine a new employee who writes well but has never read your return policy. Asking more confidently will not give them the missing rule.

RAG gives the model relevant reading material before it answers. It changes what information is available for this request; it does not teach the model permanently.

A CONCRETE EXAMPLE

Ask Can I return a sale item? Give the model the actual sentence Sale items can be exchanged within 14 days.

Now it can explain that rule instead of guessing.

Keep this idea: The benefit comes from supplying the right evidence, not from the acronym.

UNDERSTAND / 02#

What happens when a document becomes searchable?

Read the explanation

Your application reads the document, extracts its text, divides it into useful passages, and stores searchable representations with source identifiers. This preparation is often called indexing.

It usually happens before the customer asks a question. The original text must remain available because the model needs words it can read, not just numerical vectors.

A CONCRETE EXAMPLE

A three-page returns document becomes several passages. Each passage records its page and document revision so the answer can later point back to it.

Keep this idea: Indexing prepares knowledge; it does not produce the customer's answer.

Write my explanation
UNDERSTAND / 03#

What happens after the customer submits a question?

Read the explanation

The application searches the index, selects applicable passages, and adds their text to the model request alongside instructions and the customer's question. The model then writes a new answer using that supplied context.

The application should check the answer's format and whether its factual statements are supported before presenting completion.

A CONCRETE EXAMPLE

Search finds a sale-item clause and a general returns clause. Selecting the specific clause avoids applying the general refund rule to excluded items.

Keep this idea: Search, selection, generation, and checking are separate operations.

UNDERSTAND / 04#

What does the model actually receive?

Read the explanation

It receives a structured request containing instructions, the user question, and selected evidence. It does not automatically receive the entire database.

You decide which information crosses that boundary, including permissions, amount of text, and source labels. Treat retrieved instructions as document content rather than commands the model may obey.

A CONCRETE EXAMPLE

Instructions: answer only from evidence. Evidence D7: sale items allow exchange.

Question: can I get a refund? A suitable answer distinguishes exchange from an unsupported refund promise.

Keep this idea: The prompt is the model's immediate reading packet.

UNDERSTAND / 05#

What if the search finds nothing or the search service is down?

Read the explanation

These situations need different responses. No matching passage means the search completed but did not supply evidence.

An outage means the application could not establish what evidence exists. Neither result licenses a made-up policy.

Ask for a useful missing detail, abstain, or explain temporary unavailability according to the actual state.

A CONCRETE EXAMPLE

No product category: ask which item. Database timeout: offer retry.

A completed search with no rule: say the available material does not answer it.

Keep this idea: Preserve the reason you could not answer.

UNDERSTAND / 06#

Does a citation prove the answer is correct?

Read the explanation

A citation gives the reader something to inspect. It proves little if the passage is irrelevant, outdated, or does not support the attached statement.

Verify the relationship between the answer and the source, and preserve the exact revision when the rule can change. Access checks still apply when opening a citation.

A CONCRETE EXAMPLE

An answer says refunds are allowed but cites a passage about exchanges. The link works; the factual support is still wrong.

Keep this idea: A usable citation must support the specific statement.

UNDERSTAND / 07#

When is RAG the wrong tool?

Read the explanation

Use an exact database operation for facts such as an order's status or the total paid this month. Use a small fixed prompt for stable text transformation that needs no external facts.

Consider model adaptation for repeated behavior problems, but do not expect fine-tuning alone to maintain changing customer records.

A CONCRETE EXAMPLE

What is order R17's status? should reach an authorized record lookup. What does the return policy say? is a document-evidence question.

Keep this idea: Choose the information source from the task, not from a fashionable architecture.

FROM IDEA TO CODE

Read a small implementation

python

Executable standard-library miniature RAG preparation: lexical retrieval plus a model-request packet. No generation provider is called.

What this demonstrates: Ask questions about a company's changing rules.

Connect it to the case: A shop assistant answers questions using approved return rules. The rule changes without retraining the language model.

import re

DOCUMENTS = [
    {"id": "general:r1", "text": "Standard items may be refunded within 30 days."},
    {"id": "sale:r3", "text": "Sale items can be exchanged within 14 days. Refunds are not offered for sale items."},
    {"id": "shipping:r2", "text": "Delivery takes 3 to 5 days."},
]

def words(text):
    return set(re.findall(r"[a-z0-9]+", text.lower()))

def retrieve(question):
    query = words(question)
    ranked = sorted(DOCUMENTS,
        key=lambda doc: len(query & words(doc["text"])), reverse=True)
    return [doc for doc in ranked[:1] if query & words(doc["text"])]

def assemble_request(question):
    evidence = retrieve(question)
    if not evidence:
        return {"status": "insufficient_evidence", "question": question}
    return {
        "status": "ready",
        "instructions": "Answer only from the evidence. Preserve exceptions. Cite its ID.",
        "question": question,
        "evidence": evidence,
    }

packet = assemble_request("Can I return a sale item?")
assert packet["evidence"][0]["id"] == "sale:r3"
assert "14 days" in packet["evidence"][0]["text"]
assert assemble_request("ZXQ123")["status"] == "insufficient_evidence"
# Inspect packet: these are the facts an approved generator would receive.
# This tiny lexical baseline has no semantic search, production auth, or live LLM.
How to read and test this code
  1. The documents are synthetic approved articles, each with a stable source ID.
  2. retrieve selects matching text; assemble_request puts that text beside the question and instructions.
  3. No model is called. Inspect the request a generator would receive, and compare an empty search.

What is RAG, and how does a retrieval service fit into an AI application?

RAG means Retrieval-Augmented Generation. Before asking a language model to answer, your application finds relevant information and puts that information into the model request.

The model can then explain your actual document instead of guessing from its training. A retrieval service is the part that finds and returns those passages.

It does not automatically supply the chat interface, user permissions, or final answer checks.

How this works

First, prepare the documents for search: read them, split them into passages, and store those passages with searchable representations. Later, when a user asks a question, search for useful passages and send their text to the model together with the question.

These are two different workflows. Updating the searchable document can change the next answer without changing the model weights.

What could go wrong?

A search may return the wrong passage, or the model may misread the right passage. Check whether the selected source actually supports the answer.

If the required rule is missing or the search service failed, report that state rather than inventing a rule.

Why choose this approach?

RAG supports changing information and inspectable sources, but you must operate indexing, permissions, search, context selection, and evaluation. A simple structured lookup is a better choice for an exact request status or a financial total.

Why can an LLM sound confident while being wrong?

A Large Language Model predicts token sequences using learned patterns. Fluent continuation and factual verification are different capabilities.

If the prompt lacks the relevant fact, or includes ambiguous evidence, a plausible continuation can still be false. Confidence in the prose is not a calibrated probability that the service request is correct.

How this works

In the reference design, the retrieval and evidence layers supply inspectable material before a host invokes generation. an evidence-status type distinguishes missing evidence from a failed backend, giving the application a basis for abstaining or asking a follow-up question.

What could go wrong?

Presenting a citation does not establish that the citation supports the attached sentence. the retrieval service preserves evidence identity, while claim-to-evidence checking and appropriate abstention remain host responsibilities.

Why choose this approach?

Restricting answers to supplied evidence improves auditability but can reduce coverage. Allowing general model knowledge expands coverage while weakening the promise that every answer reflects the indexed corpus.

Try it yourself

Ask one answerable, one ambiguous, and one unanswerable question. Write separate expected behaviors before evaluating any generated output.

How are search, retrieval, and generation different responsibilities?

Search ranks records against a query. Retrieval includes query preparation, backend selection, constraint enforcement, candidate fetching, and optional reranking.

Generation turns the resulting evidence and instructions into a new answer. Treating these as one function hides whether an error came from missing data, ranking, or answer synthesis.

How this works

A hybrid retriever and the strategy classes orchestrate search; an evidence assembler builds a bounded evidence bundle. Their return types are useful without a chat model.

This separation also supports source verification tools and ordinary search interfaces.

What could go wrong?

A fallback that silently generates when search fails can convert an infrastructure outage into misinformation. Use strict retrieval and propagate backend failure into the host's response state.

Why choose this approach?

Explicit stages require more wiring and more status handling. They also let you benchmark retrieval independently and switch generation providers without rebuilding the corpus.

When should I use RAG instead of fine-tuning or a SQL query?

Use retrieval when answers depend on a changing collection and need source attribution. Use a structured query when the task is exact aggregation over authoritative fields.

Consider fine-tuning when the persistent problem is behavior, style, or task adaptation rather than missing up-to-date facts. These approaches can be combined.

How this works

The retrieval service's document and evidence abstractions suit passage retrieval. A question such as total approved invoices this month should usually reach a database computation; nearest passages cannot guarantee an exact total.

Fine-tuning is not implemented by this subsystem.

What could go wrong?

A semantic similarity score can make an approximate answer look exact. The host must route tasks appropriately and preserve authorization on both document search and structured tools.

Why choose this approach?

Task routing adds complexity but avoids forcing every question through a vector index. A single retrieval path is easier to prototype and easier to misuse.

Try it yourself

What is the difference between a document, a chunk, a vector, and evidence?

A document is a source-level unit of text and metadata. A chunk is a searchable subdivision.

An embedding vector is a numerical representation of that subdivision. Evidence is selected, attributed text prepared for a consuming model or user.

These objects have different lifetimes and should not share one overloaded identity field.

How this works

The canonical Chunk, Document, and SearchResult dataclasses separate ingestion and search shapes; evidence types add revision, source, span, and citation information. A chunk hit becomes useful evidence only after selection and attribution.

What could go wrong?

Confusing a chunk ID with a document ID breaks deletion, citation lookup, and version switching. the retrieval service carries metadata through the pipeline, but hosts must supply stable source identities and meaningful provenance.

Why choose this approach?

More explicit types require conversion at boundaries. They reduce accidental field loss and make changes to storage independent of the user-facing citation contract.

Try it yourself

What do dense and sparse retrieval mean?

Dense retrieval compares learned vectors, making semantic paraphrases discoverable. Sparse or lexical retrieval scores token-based signals, making exact names, identifiers, and unusual terms discoverable.

They capture different notions of relevance. Neither should be described as understanding the user's authorization or guaranteeing truth.

How this works

The retrieval service separates a vector index and a lexical index capabilities and composes them in hybrid retrieval. PostgreSQL offers native full-text search; some other adapters approximate lexical ranking with token overlap.

Those are different implementations, not equivalent language models.

What could go wrong?

Dense retrieval can confuse related concepts; lexical retrieval can miss synonyms. Hybrid fusion reduces dependence on one signal but adds its own ranking choices and cannot recover absent source material.

Why choose this approach?

Two signals increase implementation and evaluation cost. A keyword-only strategy can be preferable for exact support codes or a prototype with no embedding service.

What does grounding actually guarantee?

Grounding means giving an answer process explicit evidence it can use. It is a relationship between a service request and supporting material, not a property conferred by vector search alone.

A grounded workflow must preserve provenance, show the relevant revision, and handle insufficient evidence honestly.

How this works

An evidence assembler deduplicates, merges eligible spans, budgets rendered context, and creates citation labels. revision-aware source lookup can retrieve a bounded span from a retained revision. These mechanisms make verification possible rather than automatically performing every verification step.

What could go wrong?

A wrong retrieved passage, stale document, or unsupported inference can survive into the answer. Host-side citation checks and evaluation are still necessary; delimiter escaping is only one mitigation against untrusted source instructions.

Why choose this approach?

Strong attribution needs snapshot retention and richer metadata. Minimal text-only search is cheaper but cannot support reliable historical verification.

How do relevance, correctness, faithfulness, and freshness differ?

Relevance asks whether material addresses the question. Correctness asks whether the service request is true.

Faithfulness asks whether the answer follows the provided evidence. Freshness asks whether the evidence reflects an appropriate time or revision.

An answer can be faithful to an obsolete policy and therefore be incorrect for today's user.

How this works

The reference design separates retrieval evaluation from answer evaluation and carries freshness and revision fields in evidence. These signals allow a host to assess different failure modes rather than collapse quality into a single score.

What could go wrong?

High retrieval recall does not establish answer correctness. A heuristic overlap score also cannot establish that a reasoning step is valid or that the source itself is authoritative.

Why choose this approach?

Multiple metrics complicate release decisions but expose regressions that one average hides. The right acceptance criteria depend on the product's questions and corpus.

What are the main cost and latency stages in a RAG request?

Typical stages are query transformation, query embedding, candidate search, fusion, reranking, evidence assembly, and host generation. Ingestion has separate extraction, chunking, embedding, and storage costs.

The relative expense depends on providers, data size, network placement, and configuration; this reference design does not establish universal timings.

How this works

Separating candidate_k from final_k permits a larger search pool without necessarily sending every hit to generation. Telemetry records stage events and durations, and the embedding executor bounds concurrency and provider call duration when configured.

What could go wrong?

Increasing query variants, candidate counts, and retries together can multiply load. No single semaphore controls an entire fleet or gives an end-to-end request deadline.

Why choose this approach?

Higher candidate recall often costs more latency and money. Optimize against a quality target using measured stage distributions, not guessed millisecond service requests.

What does domain-agnostic mean, and what does it not solve?

Domain-agnostic means the core can work with different application schemas, sources, settings, and storage implementations through explicit interfaces. It does not mean every domain has identical chunking needs, permissions, legal retention rules, or quality thresholds.

Those knowledge rules remain part of the host's product design.

How this works

The retrieval service receives settings, sessions, version storage, embedders, and retrieval strategies rather than importing a host's models. The same core can serve a knowledge corpus or a support corpus while their adapters and evaluation datasets differ.

What could go wrong?

Generic abstractions can hide important domain constraints if the host never models them. A tenant filter is useful only when trusted identity selects the correct scope and every storage path respects it.

Why choose this approach?

Reusability reduces coupling but requires deliberate integration work. A specialized application may be quicker initially and harder to reuse safely later.
